## Text and context capture (Accessibility API, screen OCR, poor-AX apps)

### Takeaway
Cotypist reads the focused text field and inserts completions through the macOS Accessibility API, which is its only required permission. It optionally adds context from Screen Recording plus on-device OCR of the surrounding window, plus the app name, window title and URL. Apps that don't expose text and character geometry through AX either don't work, need an AX-enabling tweak (Google Docs accessibility mode, Chromium "Text Metrics" / `--force-renderer-accessibility=complete`), or fall back to a "mirror" window.

### Cited Findings
- CONFIRMED (1P): "Cotypist relies on the macOS Accessibility API to read the text field you're typing in and insert completions." The required permission is "Device Control and Data Access" (called Accessibility on macOS 26 and earlier). "Cotypist can't work without it." — [Troubleshooting](https://cotypist.app/help/troubleshooting)
- CONFIRMED (1P): Without the Accessibility permission "there is no autocomplete at all." Password fields are protected by macOS, except after the user clicks a site's "Reveal Password." — [Privacy overview](https://cotypist.app/help/privacy); [Privacy policy](https://cotypist.app/privacy)
- CONFIRMED (1P): Optional **Screen Recording** lets Cotypist read nearby on-screen text using "on-device text recognition." The policy says this relies on "built-in operating system capabilities," that it is enabled by default once the permission is granted during setup, and that screenshots are "processed in real time and are never stored or transmitted." — [Privacy policy](https://cotypist.app/privacy); [Privacy overview](https://cotypist.app/help/privacy)
- CONFIRMED (1P): Context captured with each text (as described for sync): "The text you typed, and the context it was written in," which covers the **app, window title, web address, and text read from the surrounding window**. — [Privacy overview / iCloud sync](https://cotypist.app/help/privacy)
- CONFIRMED (1P): Optional clipboard context (off by default, Pro only) is read "in memory only." — [Privacy overview](https://cotypist.app/help/privacy); [Pricing](https://cotypist.app/pricing)
- CONFIRMED (1P): "Cotypist needs apps to make their text fields accessible to other software on your Mac." Apps that don't expose this are "Not supported" and Cotypist can't work around them. That list includes VMs and remote desktops (Parallels, Citrix), Zed ("Zed's interface isn't visible to other apps, so Cotypist can't read text or cursor positions"), Sublime Text, OneNote, Anki, Thunderbird, Google Slides, Ghostty, cmux, Warp and Kitty. — [Compatibility](https://cotypist.app/compatibility)
- CONFIRMED (1P): Google Docs works only with Docs' own Accessibility mode enabled (Tools > Accessibility > screen reader and braille support): "Cotypist relies on Google Docs' Accessibility mode to read your document and show suggestions." — [Compatibility](https://cotypist.app/compatibility)
- CONFIRMED (1P): Arc and Dia (Chromium-based) show suggestions only in a "mirror" window above the field unless the user either enables "Text Metrics" at `chrome://accessibility` (which "may not persist after restarting the browser or switching between Spaces") or launches the browser with `--force-renderer-accessibility=complete`. Firefox and Zen "can only show suggestions in a mirror window." Safari, Chrome, Brave and Edge work out of the box. — [Compatibility](https://cotypist.app/compatibility); [Troubleshooting](https://cotypist.app/help/troubleshooting)
- CONFIRMED (1P): Terminals (Terminal.app, iTerm) activate automatically only when Cotypist detects an AI-agent prompt (Claude Code, Codex, OpenCode, pi, Kilo CLI). It handles tmux, zellij and Herdr panes, and shell completions are off by default. In VS Code, Cursor and Windsurf it works in sidebar chats; the main editor is off by default but can be enabled. A force-activate shortcut (Ctrl+`) works in other fields. — [Compatibility](https://cotypist.app/compatibility); [Shortcuts](https://cotypist.app/help/shortcuts)
- CONFIRMED (1P): Cotypist "tries to avoid activating in small fields" meant for tabbing through. Google Sheets stays idle in small cells unless force-activated. — [Shortcuts](https://cotypist.app/help/shortcuts); [Compatibility](https://cotypist.app/compatibility)
- CONFIRMED (3P, TabType clone author): Cotypist "reads chats from the screen only," meaning screen OCR is used for conversation context. TabType copies "Cotypist-style caret sanity checks" and "Cotypist's size gate" (skipping small fields). — [TabType COMPARISON.md](https://raw.githubusercontent.com/nilava/TabType/main/docs/COMPARISON.md); [TabType README](https://github.com/nilava/TabType)

### Inferences
- INFERRED: The core loop almost certainly uses the standard AX calls. It gets the system-wide `AXUIElementCreateSystemWide()` element, reads `kAXFocusedUIElementAttribute`, then `kAXValueAttribute` and `kAXSelectedTextRangeAttribute`, and `kAXBoundsForRangeParameterizedAttribute` for the caret rectangle. It probably subscribes to `AXObserver` notifications such as value-changed and selected-text-changed. Reasoning: Cotypist says it reads "the text field" and "cursor positions" through the AX API (the Zed note), and the Chromium fix it prescribes enables exactly the per-character geometry those parameterized attributes return. Cotypist does not name these attribute constants anywhere public.
- INFERRED: The Arc/Dia "Text Metrics" requirement is a strong signal that inline placement depends on per-character bounds (`AXBoundsForRange`). Chromium computes inline text-box geometry only in its fuller accessibility modes. When bounds are missing, Cotypist falls back to the mirror window. Chrome, Brave and Edge probably work out of the box because Cotypist (like screen readers) can switch Chromium's full AX tree on, for example by setting `AXEnhancedUserInterface` or `AXManualAccessibility` on the app element. Arc and Dia apparently don't honour that, or reset it, which explains the non-persistent setting. Cotypist has not confirmed any of this.
- INFERRED: Terminal support works by reading the terminal's AX text buffer (Terminal.app and iTerm expose AX text) and pattern-matching agent prompt UIs. Ghostty, Kitty and Warp render with custom GPU text and expose little or no AX text, which matches their "not supported" status.
- INFERRED: "On-device text recognition" through "built-in operating system capabilities" most likely means Apple's Vision framework (`VNRecognizeTextRequest`) running on ScreenCaptureKit or CGWindow captures of the region around or above the field. Neither framework is named.

### Gaps
- No first-party statement names specific AX attributes, `AXObserver` use, or whether Cotypist sets `AXEnhancedUserInterface`/`AXManualAccessibility` on Electron or Chromium apps.
- No information on how much surrounding text (characters or tokens) is read from the field or from OCR.
- No confirmation of which screen-capture API (ScreenCaptureKit vs. CGWindowListCreateImage) or OCR framework is used.

## Overlay rendering (ghost text, positioning, font matching)

### Takeaway
Cotypist draws grey ghost text inline at the caret when it can get caret geometry. Otherwise it falls back to a "mirror" window that shows the text plus suggestion above the field. It also places a small Cotypist icon next to active text fields, and adds numbered pickers below the cursor for alternatives and synonyms. No public statement explains how the overlay window is built or how fonts are matched.

### Cited Findings
- CONFIRMED (1P): Suggestions appear inline at the cursor as ghost text. Tab accepts the next word, and typing on overrides the suggestion. — [cotypist.app](https://cotypist.app); [MacStories sponsor post](https://www.macstories.net/sponsored/cotypist-smart-autocomplete-for-your-whole-mac-sponsor/)
- CONFIRMED (1P): Fallback: "Without setup, Cotypist shows suggestions in a 'mirror' window above the text field instead of inline" (Arc/Dia). Firefox and Zen are mirror-only. — [Compatibility](https://cotypist.app/compatibility); [Troubleshooting](https://cotypist.app/help/troubleshooting)
- CONFIRMED (1P): There is a "small Cotypist icon next to any text field" that gives quick access to per-app toggles. Option-clicking it sends a normal Tab. — [Tips](https://cotypist.app/help/tips); [Shortcuts](https://cotypist.app/help/shortcuts)
- CONFIRMED (1P): Word Alternatives (Labs, Pro) shows "a short, numbered list of other words" right below the cursor, chosen by pressing a number. Synonyms for selected text work the same way. — [Tips](https://cotypist.app/help/tips)
- CONFIRMED (3P, TabType): TabType's v2.0 "felt worse" than Cotypist because "the ghost sat in the wrong place, appeared late." For v2.1 it adopted "Cotypist-style caret sanity checks, snap to the line, retry at 40/80/160 ms, a per-field line-height cache," plus a "text mirror preview per app," which it lists under features that match Cotypist. — [TabType README](https://github.com/nilava/TabType); [TabType COMPARISON.md](https://raw.githubusercontent.com/nilava/TabType/main/docs/COMPARISON.md)
- CONFIRMED (3P, reviewer): A reviewer writes that both Cotypist and Cotabby are "a bit hacky" in how they find the cursor and overlay suggestions, and that this can break the layout in some apps. — [Ole Reissmann, Jun 2026](https://olereissmann.com/cotypist-and-cotabby-local-ai-autocomplete-for-writers/)
- Supporting context only (not Cotypist): The open-source clone Typist sizes its ghost text from the caret height, so it does not exactly match the host font — [Typist GitHub](https://github.com/BrodySalvucci/Typist). A generic "Cotypist-like" build plan uses a borderless, non-activating `NSPanel` at the `AXBoundsForRange` rectangle — [canivibecodeit.com](https://canivibecodeit.com/cotypist) (generic plan, not Cotypist documentation).

### Inferences
- INFERRED: The inline ghost text is almost certainly a borderless, transparent, non-activating, click-through `NSPanel`/`NSWindow` at a high window level, placed at the AX caret rectangle. A third-party app can't draw inside another app's text view on macOS, and the mirror-window fallback for fields with no bounds fits an overlay window that needs a caret rectangle.
- INFERRED: Font matching is probably approximate. AX rarely exposes a field's font reliably (some fields expose `AXAttributedStringForRange` with font attributes; many web and Electron fields don't). The "per-field line-height cache" and "snap to the line" behaviour TabType attributes to Cotypist suggests sizing from the caret/line rectangle height, possibly refined with attributed-string font info where available.
- INFERRED: "Caret sanity checks" probably mean rejecting implausible bounds (zero-size rects, rects outside the window, stale geometry right after a keystroke) and retrying after short delays before showing the ghost text.

### Gaps
- No developer comment found on font, size or colour matching with the host app, on window type and level, or on how the ghost text avoids being captured by screenshots or AX.
- No detail on how the overlay follows scrolling, multi-line wrapping or mid-line completion (a Pro feature).

## Key interception and text insertion

### Takeaway
Tab (next word), the key above Tab (full completion), Esc (dismiss/pause) and a few other shortcuts are captured globally only while a suggestion is showing, and Option+Tab passes a real Tab through. Accessibility is the only required permission. Insertion uses per-app strategies, including typing and pasting: for longer completions Cotypist confirms it briefly uses the clipboard, restores the user's original contents, and marks the temporary content so clipboard-history tools ignore it.

### Cited Findings
- CONFIRMED (1P): Keys. Tab inserts the next word. The key above Tab (`, §, or ^) accepts the full completion. Ctrl+` force-activates. Ctrl+Option+Cmd+` toggles per app for a few minutes. Option+Tab "sends a regular Tab." Esc dismisses and briefly pauses, and "once no suggestion is showing, Esc passes through to the app." Shortcuts are user-configurable through a recorder field, and on non-US layouts "the physical key you press is what counts." — [Shortcuts](https://cotypist.app/help/shortcuts); [Tips](https://cotypist.app/help/tips)
- CONFIRMED (1P): Conflicts: Grammarly also uses Tab. Karabiner-Elements and TextExpander can intercept keys. **Secure Input** (often turned on by password managers, or by Terminal/iTerm "Secure Keyboard Entry") "can block single-key shortcuts system-wide." Two running Cotypist instances can insert text twice. The troubleshooting page also says "Apps register 'event taps' with macOS to watch your keyboard and mouse" and lists known fixes for slowdowns (Karabiner-Elements 16.1.9, Mos after 4.2.1). — [Troubleshooting](https://cotypist.app/help/troubleshooting)
- CONFIRMED (1P): The only required permission is Accessibility. The troubleshooting page does not mention Input Monitoring. — [Troubleshooting](https://cotypist.app/help/troubleshooting); [Privacy policy](https://cotypist.app/privacy)
- CONFIRMED (1P): The Accessibility permission lets the app "read text field contents and insert completions." — [Privacy policy](https://cotypist.app/privacy)
- CONFIRMED (1P): Clipboard use during insertion: Cotypist "may also briefly use the clipboard for longer completions," and "will try to save your original clipboard contents beforehand and restore them immediately afterwards." It marks the temporary content so clipboard history tools can ignore it. — [Privacy overview](https://cotypist.app/help/privacy); [Privacy policy](https://cotypist.app/privacy)
- CONFIRMED (3P, TabType): TabType lists the following under features that match Cotypist: "Listen-only key tap" and "Per-app insertion workarounds (typing / per character / chunks / paste / first word typed". In TabType's own design, the listen-only tap observes keystrokes, and "Tab, ⇧Tab, and Esc act as system hotkeys only while a suggestion is showing." — [TabType COMPARISON.md](https://raw.githubusercontent.com/nilava/TabType/main/docs/COMPARISON.md); [TabType README](https://github.com/nilava/TabType)
- Supporting context: The open-source competitor Cotabby asks for both Accessibility and Input Monitoring. — [Cotabby comparison page](https://cotabby.app/cotypist-alternative)

### Inferences
- INFERRED: Cotypist probably uses a keyboard `CGEventTap` to observe typing; the troubleshooting text implicitly puts Cotypist among apps that register event taps. It swallows Tab, the key above Tab and Esc only while a suggestion is visible. That could be done either with a temporarily registered global hotkey (the TabType description) or by returning NULL from an active tap. The Secure Input symptom ("blocks single-key shortcuts") fits both, since Secure Event Input blocks both taps and Carbon hotkeys for other processes. The recorder-style shortcut UI suggests a hotkey library, possibly one built on `RegisterEventHotKey`. That is speculative.
- INFERRED: Cotypist never asks for Input Monitoring, which suggests an Accessibility-trusted process is allowed to create its keyboard tap. As I understand macOS TCC rules, AX-trusted apps can create event taps, and Input Monitoring is needed only for listen-only taps by non-AX-trusted apps. Its posting of synthetic events falls under the Accessibility grant.
- INFERRED: Short completions (one word on Tab) are probably inserted by synthesized key events (`CGEventKeyboardSetUnicodeString`, per character or in chunks), or by setting `kAXSelectedTextAttribute` where an app honours it. Longer completions use a pasteboard swap plus a synthesized Cmd+V, followed by restoring the clipboard. The "first word typed" workaround (per TabType) suggests typing the first word as keystrokes so the host app's own autocorrect, undo and input handling register it, then pasting the rest.
- INFERRED: "Marks the temporary content so clipboard history tools can ignore it" most likely means the nspasteboard.org conventions (`org.nspasteboard.TransientType` / `org.nspasteboard.ConcealedType`). Cotypist doesn't name them.

### Gaps
- No first-party confirmation of the CGEventTap type (active vs. listen-only) or of whether Carbon hotkeys are used.
- No first-party breakdown of which insertion method is used per app, or the length threshold at which paste replaces typing.

## Inference engine, models, prompt construction and latency

### Takeaway
Cotypist runs **llama.cpp** locally on Apple Silicon. The default model is **Google Gemma 4 E2B**, shipped as Cotypist's own quantization (about 3.4 GB file, about 1 GB active memory). Larger Macs can use E4B (about 2.5 GB in memory), and the catalog also includes Gemma 3 1B/4B, Qwen 3 1.7B/4B, and on Pro, Gemma 4 26B A4B, Qwen 3 8B and Qwen 3 30B-A3B. Third-party analysis says Cotypist uses a delimited, token-budgeted, sectioned prompt with encrypted delimiters, a beam search over phrases, fixed length targets of 2/4/7/10 words, and no fixed debounce. There are no official latency numbers beyond "no noticeable delay."

### Cited Findings
- CONFIRMED (1P): "Gemma 4 by default, running locally through **llama.cpp**." The press kit also cites a 3 GB Gemma model and about 1–2.5 GB RAM for real-time completions. — [Press Kit](https://cotypist.app/press)
- CONFIRMED (1P, developer on Product Hunt): "The default is Google's Gemma 4 E2B, running entirely on your Mac." The model is a few GB on disk but needs only about 1 GB of active memory, because weights are streamed from disk as needed rather than held in GPU memory. M-series Max and Ultra Macs can use the larger E4B (about 2.5 GB in memory), and heavier models are offered only on machines that can run them well. "it winds down and frees that memory when you're not actively typing." On speed: "Suggestions appear in real time, usually with no noticeable delay, and they keep updating as you write." — [Product Hunt, maker replies (~Jun 2026)](https://www.producthunt.com/products/cotypist)
- CONFIRMED (1P): Model catalog. Free and Plus: Gemma 4 E2B, Qwen 3 1.7B, Gemma 3 1B, Gemma 4 E4B, Qwen 3 4B, Gemma 3 4B. Pro adds Gemma 4 26B A4B, Qwen 3 30B-A3B and Qwen 3 8B. Cotypist recommends the model your Mac "runs smoothly," and heavier models take longer per word. — [Pricing](https://cotypist.app/pricing)
- CONFIRMED (1P): The menu bar icon shows download progress while a model is being fetched, and Cotypist "can't suggest anything until its AI model is in place." In other words, models are downloaded after install, not bundled. — [Troubleshooting](https://cotypist.app/help/troubleshooting)
- CONFIRMED (1P): The recommended Mac is an M1 Pro or M2 with 16 GB or more. The app uses about 1–2.5 GB of memory while active, and completions "should appear almost instantly" on recommended specs. — [cotypist.app](https://cotypist.app)
- CONFIRMED (1P): Completion length is configurable on Plus and Pro. Mid-line completion is Pro only. Custom AI instructions (global, with per-app/per-domain text "appended after the global instructions") are used "when generating every suggestion." The default instructions are pre-filled from the Mac's language and region. — [Pricing](https://cotypist.app/pricing); [Personalization](https://cotypist.app/help/personalization)
- CONFIRMED (1P): Inline autocorrect and a typo indicator, plus emoji via colon shortcodes. Multilingual, including mid-sentence language switching. — [cotypist.app](https://cotypist.app); [Press Kit](https://cotypist.app/press)
- CONFIRMED (3P, TabType): "Cotypist ships its own Gemma 4 E2B quantization." The file is 3.4 GB, against 2.5 GB for TabType's Qwen3-4B. Run inside TabType, "Cotypist's model file was ~50 ms faster but saved 20% fewer characters" (1.17 vs 1.46 on the author's writing; 3.12 vs 3.64 on the seed set). Conclusion: "The model isn't Cotypist's edge." — [TabType README](https://github.com/nilava/TabType); [COMPARISON.md](https://raw.githubusercontent.com/nilava/TabType/main/docs/COMPARISON.md)
- CONFIRMED (3P, TabType): "Cotypist wraps prompt parts in delimited, token-budgeted sections," and "its delimiters are encrypted." Cotypist uses a "9-wide beam search over whole phrases (Cotypist's search)" and lets the beam replace the first word. A word being typed that "can't become a real word gets no suggestion (as Cotypist does)." Lengths are short/medium/long/very long = "2 / 4 / 7 / 10 words." "No fixed waits" (no debounce) matches Cotypist. "Cotypist's values couldn't be recovered" (thresholds). — [TabType README](https://github.com/nilava/TabType); [COMPARISON.md](https://raw.githubusercontent.com/nilava/TabType/main/docs/COMPARISON.md). Caveat: TabType's documents attribute these items to Cotypist without saying, claim by claim, whether each came from observed behaviour or from inspecting the app bundle.
- CONFIRMED (3P): An earlier report (undated, older pricing) said the primary model was **Qwen 2.5 1.5B**, chosen because larger models would miss the latency budget, with a full cycle of roughly "100–200 milliseconds if you're moving quickly." — [Implicator.ai](https://www.implicator.ai/cotypist-the-german-indie-behind-ai-autocomplete-everywhere/). Conflicts with the current first-party default (Gemma 4 E2B) and probably describes a pre-launch build. The 100–200 ms figure is not attributed to the developer.
- CONFIRMED (3P): During the April 2026 beta, users mentioned a "better model (Gemma 3 4B)" alongside a "basic one." — [MPU Talk, Apr 10 2026](https://talk.macpowerusers.com/t/trying-cotypist-beta/45111)
- CONFIRMED (3P): Reviewers report a noticeable battery cost on laptops. — [Nic's notes, 31 May 2026](https://notes.nicolasdeville.com/apps/cotypist/). One review suggests very fast typists can outrun suggestions. — [note.com (Jun 2026)](https://note.com/kazu_t/n/n5acf7c6d595d?hl=en)
- Conflicting/unclear: One review lists "Apple's built-in model" and "bring your own model" among the choices, but the passage mixes Cotypist and Cotabby. Cotabby offers Apple Intelligence and BYO GGUF, and Cotabby's comparison page says Apple Intelligence is "Not listed as an engine" for Cotypist. — [Ole Reissmann](https://olereissmann.com/cotypist-and-cotabby-local-ai-autocomplete-for-writers/); [Cotabby comparison](https://cotabby.app/cotypist-alternative)

### Inferences
- INFERRED: "Weights streamed from disk as needed rather than held in GPU memory" fits two things: llama.cpp's default `mmap` loading, and especially the design of Gemma 3n/Gemma 4 "E" (effective-parameter) models. Their large **Per-Layer Embedding** tables can stay off the accelerator and be paged in from flash. That is why a file of about 3.4 GB runs in about 1 GB of active memory. The "E2B/E4B" naming (about 2B/4B effective parameters) supports this.
- INFERRED: The model is very likely used as a raw-continuation (base-style) predictor, even if the weights are instruction-tuned checkpoints. Reasons: beam search over phrases, fixed word-count targets, the "can't become a real word" gate, and the ~50 ms difference when its file runs in a base-model pipeline. Custom instructions and context would be injected as delimited sections ahead of the text being continued. Cotypist does not say whether it uses base or instruct checkpoints, or a fine-tune. "Ships its own quantization" doesn't establish a fine-tune.
- INFERRED: Low latency probably comes from: (1) small effective-parameter models on Metal through llama.cpp; (2) reusing the KV/prompt cache across keystrokes, since the prefix (instructions, screen context, earlier text) is stable and only the tail changes; (3) no fixed debounce, with each keystroke cancelling and restarting generation and stale results thrown away; (4) short targets (2–10 words) with beam search; (5) keeping the model resident while typing and unloading on idle. Items (2) and (3) are standard practice and fit "keeps updating as you write" and TabType's "no fixed waits," but Cotypist has not confirmed KV caching.
- INFERRED: "Encrypted delimiters" suggests the prompt template is obfuscated inside the app bundle to prevent copying, meaning someone did look inside the bundle.

### Gaps
- No official latency numbers (ms per suggestion, tokens/s) and no stated debounce timing.
- No confirmation of quantization type (Q4_K_M etc.), context-window size, KV-cache reuse, speculative decoding or MTP.
- No confirmation of whether models are base or instruct, or fine-tuned by Accelerated Thought. "Its own quantization" is all that is known.
- No information on where models are downloaded from (Hugging Face vs. their own CDN). The privacy policy lists Cloudflare as a CDN, which may be relevant. — [Privacy policy](https://cotypist.app/privacy)

## Personalization (on-device learning, retrieval, fine-tuning)

### Takeaway
Personalization is opt-in. An encrypted local database records your writing, and a "derived personalization profile" built from it drives a "Personalize word choice" strength slider that "nudges" the model toward your vocabulary. Custom instructions apply globally and per app or domain. Nothing public mentions on-device fine-tuning or LoRA. The mechanism looks like local profile/statistics-based biasing plus prompt context, not weight updates.

### Cited Findings
- CONFIRMED (1P): "Record your writing for personalization" is off by default. By default it records only fields where a completion was accepted, with an optional toggle to record every monitored text. Short texts and password fields are never recorded, and recording can be turned off per app or domain. — [Personalization](https://cotypist.app/help/personalization)
- CONFIRMED (1P): "Your typing history is stored in an encrypted local database," with "the encryption key [in] your macOS Keychain." A "derived personalization profile used by the word-choice slider" "nudges the AI toward words and phrases you actually use, rather than the statistically 'average' choice." The slider runs Off / Low–Medium / Strong, and Strong "can override a better-fitting word in favor of a frequently used one." Deleting data reverts suggestions to unmodified model behaviour. — [Personalization](https://cotypist.app/help/personalization); [Privacy overview](https://cotypist.app/help/privacy)
- CONFIRMED (1P): The profile is "a small profile of your writing style," encrypted, Mac-only, and "never synced." Writing history (not the profile) can sync through iCloud with end-to-end encryption (Labs, 2026.4). — [Privacy overview](https://cotypist.app/help/privacy); [MacSparky, Oct 2026](https://www.macsparky.com/blog/2026/10/cotypist-2026-4-syncs-your-writing-between-macs/)
- CONFIRMED (1P, developer): "Cotyist learns your voice locally" (sic). "The adaptation is a mix of both 'global' and context-specific." — [Product Hunt](https://www.producthunt.com/products/cotypist)
- CONFIRMED (1P): Slider ranges are tiered: Free up to the 2nd tick, Plus up to the 4th, Pro up to the 6th. — [Pricing](https://cotypist.app/pricing)

### Inferences
- INFERRED: A "strength" slider that can override "a better-fitting word in favor of a frequently used one" reads like decode-time logit biasing or beam re-ranking. A word/phrase frequency profile, global and per app/domain, would add a scaled bonus to candidate tokens or phrases. The sentence would be odd for fine-tuning or LoRA. Retrieval of past snippets into the prompt is also possible; the "context-specific" adaptation could be per-app retrieval, but nothing confirms it.

### Gaps
- No public description of the profile's contents (n-grams? embeddings?), whether recorded text is retrieved into prompts, or whether any on-device fine-tuning happens.

## Language, stack and open-source dependencies

### Takeaway
The confirmed third-party components are llama.cpp (inference), Sentry (crash reports), Google BigQuery and Fathom (anonymous analytics), Paddle (payments), and, per TabType, Sparkle (auto-updates). Cotypist publishes no acknowledgements or third-party-licence page that I could find, and has not stated its language or UI framework.

### Cited Findings
- CONFIRMED (1P): llama.cpp — [Press Kit](https://cotypist.app/press).
- CONFIRMED (1P): Sentry ("data stored in Frankfurt") and Google BigQuery for anonymous usage counts; Fathom for analytics; Paddle for checkout; Cloudflare CDN; Hetzner hosting; Mailcoach email; Replies support. ### Inferences
- INFERRED: Distribution outside the Mac App Store is required, because the App Store sandbox doesn't allow system-wide AX control or event posting into other apps. Notarized DMG plus Sparkle is the standard alternative.
- INFERRED: The app is very likely native Swift with AppKit (and probably SwiftUI for settings), linking llama.cpp as a C/C++ library or xcframework with the Metal backend. Reasons: the developer is a long-time native Mac developer (Timing), and it uses a menu-bar app, Keychain, iCloud Keychain and CloudKit-style sync, and Sparkle. No source confirms the language.

### Gaps
